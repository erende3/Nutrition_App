# 4. Current iOS architecture (Phase 3)

The app has 16 Swift files and about 1,544 lines. There is no shared client state: every screen owns `@State` copies of what it fetched.

## 4.1 Who owns what

| State | Owner | Kind | Notes |
|---|---|---|---|
| `UserProfile?`, `isLoading`, `errorMessage` | `RootView` | `@State` | Loaded once in `.task`. Retry reloads it. Only used to choose between onboarding and `ContentView`. |
| Onboarding fields, `bmr`, `tdee`, `dailyCalorieGoal`, `isLoading`, `errorMessage` | `OnboardingViewModel` (`ObservableObject`) | `@StateObject` in `OnboardingView` | Calls `APIClient.shared` directly. |
| `dailyGoal = 2200`, `caloriesConsumed = 0`, `caloriesRemaining = 2200` | `DashboardView` | `@State` | **Server-derived, with fake initial values.** |
| `errorMessage` (one for everything) | `DashboardView` | `@State` | Shared by summary load, estimate and photo preparation. |
| `mealText`, `lastResult`, `isLoading` (estimate), photo state (`photo`, `cameraImage`, `isPreparingPhoto`, `photoGeneration`, `showingCamera`, `libraryItem`) | `DashboardView` | `@State` | View-local UI state (correct place). |
| `meals`, `isLoading`, `errorMessage` | `MealHistoryView` | `@State` | A separate copy of today's meals. |

**Duplication.** Today's data exists twice. The Dashboard has totals derived from meals, and History has the meals themselves. They are fetched separately and synchronized only by accident of the tab lifecycle (see 4.3).

## 4.2 Every direct `APIClient` call

| Call site | Endpoint | Trigger |
|---|---|---|
| `RootView.swift:58` `loadProfile` | `GET /users/profile` | `.task` on launch; Retry; onboarding completion |
| `OnboardingViewModel.swift:44` | `POST /users/onboarding` | "Calculate My Goal" |
| `ContentView.swift:281` `estimateMeal` | `POST /meals/estimate` (saves the meal) | "Estimate Meal" |
| `ContentView.swift:355` `refreshDailySummary` | `GET /summary/daily` | Dashboard `.task` (line 258); after a successful estimate |
| `MealHistoryView.swift:87` `loadMeals` | `GET /meals/today` | History `.task`; pull-to-refresh; Retry |
| `MealHistoryView.swift:97` `deleteMeal` | `DELETE /meals/{id}` | swipe to delete |

Summary is loaded in one place, meals in one place and the profile in one place. There are no duplicate loaders, but they are independent copies, and none can be unit-tested, because the views call the `APIClient.shared` singleton.

## 4.3 State and data flow traces

| Flow | What happens today |
|---|---|
| App launch | `RootView.task` → profile. If onboarded, `ContentView` (a `TabView`) builds the Dashboard, whose `.task` loads the summary. History's `.task` runs only when its tab is first shown. |
| Onboarding completion | The backend saves the profile at "Calculate My Goal". "Continue to Dashboard" calls `onComplete`, which reloads the profile; `ContentView` appears and the Dashboard loads. |
| Dashboard load | One `GET /summary/daily`. Until it returns, the ring shows **2200 left / Consumed 0 / Goal 2200**, which are placeholders, not data. |
| Summary load failure | Red text at the bottom of the Dashboard. The numbers keep their previous or placeholder values. **There is no Retry.** |
| History load | `isLoading = true` replaces the whole list with a spinner on **every** load (tab appearance and pull-to-refresh), then shows the list, the empty state, or a full-screen error with Retry. |
| Meal estimation | `isLoading`; `errorMessage = nil` (this also erases a photo error); `POST /meals/estimate`. On success: `lastResult`, clear the text, clear the photo if no newer pick, then `refreshDailySummary()`. History is not told. |
| Successful save | Dashboard totals refetched. History refetches only when its tab next appears. |
| Meal deletion | `DELETE`, then remove the row locally. The Dashboard is not told. A delete failure sets History's `errorMessage`, which **replaces the list with the full-screen error**. |
| Background → foreground | **Nothing.** No `scenePhase` observer anywhere; `.task` does not re-run on foregrounding. |
| Network failure | The request fails with `APIError.transport` ("Can't reach the server at …" / "You're offline"). |
| Retry | Root: reload the profile. History: `loadMeals()`. **Dashboard: none.** |
| Network change | No observer. Recovery needs a new request, which only Retry (Root/History), pull-to-refresh (History), a tab switch or a new estimate makes. |
| Photo preparation | An unretained `Task` (`ContentView.swift:327`) loads the image, then JPEG-encodes it in `Task.detached`. `photoGeneration` makes the newest pick win. |
| Photo failure | `errorMessage = "Couldn't load / prepare that photo…"`. Any earlier photo is kept. The error can be erased by the next summary refresh (0.6 Minor #8). |
| API error presentation | `error.localizedDescription` from `APIError`, shown as red text (Dashboard, onboarding) or a full-screen message plus Retry (Root, History). |

**Tab lifecycle.** SwiftUI's `TabView` keeps both tabs' views (and their `@State`) alive. It fires `onAppear`/`.task` each time a tab is selected and cancels the `.task` when the tab is left. So today, switching tabs is the de facto sync mechanism: Dashboard → History refetches meals, and History → Dashboard refetches the summary. This is standard SwiftUI behavior but is not asserted by any test; acceptance step A3 confirms it on the device.


# 5. Root cause of the stale Dashboard, and what 0.6 proves (Phases 3 and 5)

## 5.1 Is any networking state stale?

| Candidate | Finding |
|---|---|
| `URLSession` | `APIClient.shared` uses `URLSession.shared`. It keeps a connection pool, but a connection to an address that disappeared fails that request, and the next request opens a new connection. Nothing is cached per network in app code. |
| `API_BASE_URL` | Read once from Info.plist into `AppConfig.baseURL` (a static constant). It is the Mac's **`.local` Bonjour name** (confirmed in `Local.xcconfig`, which was only read), not an IP, so it doesn't change when the network does. |
| `.local` resolution | Done by the system (mDNSResponder) for each new connection. The app caches no address. |
| `APIClient` | Immutable: `baseURL`, `session`, a timezone closure and a decoder. No retry state, no reachability flag. |

**Nothing in the networking layer can hold stale state** across a network change, beyond a single request that may fail on a dead pooled connection.

## 5.2 Why the Dashboard stays stale

The Dashboard runs one request, from `.task`, when the view appears. After that, the only things that call `refreshDailySummary()` are a successful estimate and re-selecting the Dashboard tab. So:

- **Staying on the Dashboard**, with the server gone and back, or the network switched, nothing ever re-requests. The numbers stay as they were. If the failure happened while loading, the red error text stays and there's no button to retry.
- **Going to Settings to switch Wi-Fi and coming back** does not re-run `.task`: there is no `scenePhase` handling. This is exactly the 0.5 "didn't reconnect by itself" scenario.
- **A launch-time failure** leaves "2200 calories left / 0 / 2200" on screen, which look like real data.

History, by contrast, has Retry and pull-to-refresh, so it recovers as soon as you ask it to.

**Conclusion.** The stale Dashboard is fully explained by the **missing refresh triggers** (Retry, pull-to-refresh, foreground) plus **placeholder values presented as data**. It is not explained by URLSession or name resolution. No code path could let the Dashboard recover on its own.

## 5.3 What the 0.6 network-switch result proves, and what it doesn't

**It proves:**

- After the Mac and iPhone moved networks, a fresh request from the **same running process** (same `URLSession.shared`, same `.local` URL) succeeded immediately.
- So no relaunch is needed, and the Dashboard would recover the same way if it had any way to make a new request.

**It does not prove:**

- That recovery happens **without user action**. Nothing in the app retries on its own, and 0.7 will still need a trigger.
- That the **first** request after a switch always succeeds. A request on a dead pooled connection can still fail once, which is why a visible Retry matters.
- Anything about **Dashboard-specific** code. The Dashboard was never retried in 0.6, because it has no Retry.
- Anything about a switch **while a request is in flight** (for example, a 300 s estimate), cellular fallback, or the Mac getting a slow mDNS update. Those are covered by acceptance steps, not by the design.

**Implication.** No connectivity monitoring (`NWPathMonitor`) is needed. The plan relies on real request results plus the three user-reachable triggers (Retry, pull-to-refresh, becoming active).


# 6. Architecture alternatives and recommendation (Phase 4)

| Concern | A. View-owned state plus triggers | B. Shared `@Observable` store at the root | C. Per-screen view models |
|---|---|---|---|
| Summary | Dashboard `@State` | store | `DashboardModel` |
| Meals | History `@State` | store | `HistoryModel` |
| Profile | `RootView` | `RootView` (not moved) | `RootView` |
| After create | Dashboard refetches the summary; History waits for its tab | store refetches both; both screens update | same as A, or models must talk to each other |
| After delete | History removes the row; Dashboard waits for its tab | store refetches both | same as A |
| Refresh | each screen adds Retry, pull and foreground handling (twice) | one `refresh()`, called by the triggers | each model adds them |
| Loading / error | per view, untestable | in the store, testable | in each model, testable |
| Testability | none: views call a singleton | store tests with the stubbed `URLSession` | good, but two models |
| SwiftUI lifecycle | `.task` cancellation reaches the requests (M4) | refresh runs in a store-owned task, so leaving a tab doesn't cancel it | as A unless the model owns the task |
| Stale-state risk | medium: sync depends on tab switches | low: one copy of today's data | medium |
| Extra requests | every tab switch refetches | none on tab switch; fetches happen on real triggers | as A |
| Complexity | lowest code, but duplicated logic | one new file (~120 lines) | two new files and duplicated sync |
| Migration cost | small edits in two views | moderate: two views rewired | moderate |

**Recommendation: B, kept narrow.** Summary and meals are two views of the *same* server fact ("today"), so they belong in one place and are fetched together. A small store removes the duplication rather than moving it, because Dashboard and History read the same `meals` and `summary` values, and it is the only option that makes the refresh and error logic unit-testable. A would fix the visible symptom but keep two copies of "today", duplicate Retry, pull and foreground logic in two views, and leave everything untested. C adds testability but keeps the duplication and the need for cross-screen sync. The roadmap already chose B (decision #11); this investigation confirms it for concrete reasons, not by default.

## 6.1 What goes in `NutritionStore`, and what doesn't

| In the store (shared) | View-local (not in the store) |
|---|---|
| `summary: DailySummary?` (nil = never loaded) | meal-estimation text, `lastResult` |
| `meals: [Meal]?` (nil = never loaded) | estimate in progress, **estimate error** |
| `isRefreshing: Bool` | selected / prepared photo, photo preparation state, **photo error** |
| `loadError: APIError?` (last refresh failure; cleared on success) | picker and camera presentation |
| `refresh()`, `logMeal(message:imageData:) -> NutritionEstimate`, `deleteMeal(_:)` | delete error (History, one alert) |
| the injected `APIClient` | onboarding fields, results and errors (`OnboardingViewModel`) |
| | the profile (`RootView` gate; nothing else reads it) |

The store is `@MainActor @Observable final class NutritionStore`, created with `@State` in `MyNutritionPalApp` and passed down with `.environment(store)`. It takes an `APIClient` (default `.shared`), so tests pass a stubbed one. No protocol is needed.

**Why the profile stays out.** Only `RootView` reads it, and only to choose between onboarding and the tabs. The Dashboard's goal comes from the summary. Moving it would add code with no consumer. Revisit in Phase 5 (Settings).


# 7. Refresh and lifecycle model (Phase 5)

| Event | Behavior |
|---|---|
| App launch | `RootView` loads the profile (unchanged). When `ContentView` appears (onboarded), `.task { await store.refresh() }` runs once. Summary and meals load **in parallel** (`async let`) and are applied **together**, so the two screens never disagree. |
| Onboarding completes | same path: profile reload → `ContentView` appears → one refresh. |
| Tab switch | **No network call.** Both tabs read the store. (This removes today's refetch on every tab switch.) |
| Becoming active | `ContentView` watches `scenePhase`; on a change **to `.active`**, `store.refresh()`. This covers returning from Settings, Control Center (inactive → active) and the app switcher. There's no throttle: two small GETs on a LAN are cheap, and refreshes are coalesced (see below). This also fixes a day rollover while the app sits in the background. |
| Pull to refresh | **Both** screens (`.refreshable { await store.refresh() }`). |
| Retry | the error banner's button calls `store.refresh()`. |
| After meal creation | `logMeal` → `POST /meals/estimate` → a **refetch** of both. There is no optimistic insert: the estimate response has no meal id or `created_at`, so the app can't build a `Meal` row. Server totals stay the single source of truth. |
| After meal deletion | on server success, remove the row locally at once (smooth swipe), then **refetch** both (the summary must change). On failure, the row stays and an alert shows the message. |
| Network failure → recovery | Old data stays visible with a "Couldn't update" banner and Retry. Recovery comes from Retry, pull-to-refresh or becoming active, using real request results. **No `NWPathMonitor`**, and no automatic retry loop (the no-retry rule in `APIClient` stays, because an estimate saves a meal). |

**Concurrency rules** (all tested):

1. **Coalescing.** If a refresh is in flight, `refresh()` awaits that same task instead of starting another. The launch `.task` and the first `.active` can't double-fetch.
2. **After a mutation, fetch fresh.** `logMeal` and `deleteMeal` wait for any in-flight refresh and then start a *new* one. Otherwise a refresh that started before the delete could put the deleted meal back.
3. **The refresh task belongs to the store** (an unstructured `Task` it keeps). A view that disappears only stops *waiting*; the request isn't cancelled. This removes most sources of M4.
4. **All or nothing.** If either GET fails, neither value changes and `loadError` is set. On success both are replaced and `loadError` is cleared.

# 8. Loading, empty and error states (Phase 6)

No enum is needed. Each screen's state follows from the store's four fields:

| Data | `isRefreshing` | `loadError` | Dashboard | History |
|---|---|---|---|---|
| nil | true | nil | ring and cards show "–" with a small spinner | "Loading meals…" |
| nil | false | set | "–" plus an error banner with Retry | full-screen message with Retry (ContentUnavailableView style) |
| nil | true | set | banner Retry shows a spinner (retrying) | spinner |
| present | any | nil | numbers | list, or "No Meals Yet" if empty |
| present | true | nil | numbers stay; refresh control / small indicator | **list stays**; pull-to-refresh spinner only |
| present | any | set | numbers stay, plus a banner: "Couldn't update today's totals." with the message and Retry | list stays; the same banner as the first row |

**Changes from today:**

- The fake 2200 / 0 values are gone (`summary` is optional).
- History never swaps the list for a spinner once it has data. This also stops `.refreshable` from tearing down its own list mid-refresh, a likely source of "The request was cancelled" (M4).
- A delete failure no longer hides the list.

**Separate errors so that operations don't overwrite each other** (fixes 0.6 Minor #8):

| Error | Owner | Set by | Cleared by |
|---|---|---|---|
| load error | store | failed refresh | successful refresh |
| estimate error | Dashboard | failed `logMeal` | the next estimate attempt |
| photo error | Dashboard / photo model | failed photo load or prepare | a new pick, Remove, a successful estimate |
| delete error | History (alert) | failed delete | dismissing the alert |
| onboarding error | `OnboardingViewModel` | unchanged | unchanged |

A summary refresh can then never erase a photo or estimate error, and a refresh failure after a *successful* estimate shows only as the load banner. The "Last meal added" card still confirms that the meal was saved. There's no global error framework: four plain optionals.

A small `LoadErrorBanner(message:isRetrying:retry:)` view, placed in `ContentView.swift` next to `StatCard`, is used by both screens.


# 9. Photo preparation cancellation (Phase 7)

**Today.** `preparePhoto` (`ContentView.swift:321`) creates an unstructured `Task` that nothing keeps. It awaits `item.loadTransferable(type: Data.self)` (for an iCloud photo this downloads the original), then JPEG-encodes it in `Task.detached`. `isPreparingPhoto` hides the previous photo and disables Estimate until the task ends.

| Situation | Today |
|---|---|
| Another photo picked | `photoGeneration` bumps; the old task keeps running (still downloading) but its result is dropped. The newest pick wins (correct). |
| Remove tapped | Not possible: Remove appears only when not preparing. |
| View disappears | Tabs keep `DashboardView` alive, so the task finishes and its result applies. Nothing breaks. |
| Slow iCloud load | "Preparing photo…" with **no way out**; Estimate stays disabled (0.6 Minor #3). |

**Design (smallest robust one).** Move the preparation state out of the view into a small view-owned `@MainActor @Observable final class PhotoDraft` (new file, about 60 lines). The struct `PreparedPhoto` moves with it. The class holds:

- `photo`, `isPreparing`, `error`, plus the private `generation` and a kept `task`;
- `prepare(_ load: @escaping () async -> UIImage?)`, which cancels the previous task, bumps the generation, clears the error and starts a new task;
- `cancel()`, which cancels the task, bumps the generation, and sets `isPreparing = false`. It shows **no error** and **keeps the previous prepared photo**. This is the same rule as a failed pick: "if this one fails, any earlier photo stays";
- `remove()` and `clearAfterEstimate(submittedGeneration)`, the existing "keep a photo picked while the estimate ran" rule.

**UI.** Show `ProgressView  Preparing photo…  [Cancel]` (a plain text button). Estimate stays disabled while preparing, which is unambiguous about which photo would be sent; Cancel is the way out.

**Where cancellation lands.**

| Phase | Effect of `cancel()` |
|---|---|
| During `loadTransferable` | the UI returns immediately (generation bump). `task.cancel()` asks the system to stop the load. Whether PhotosUI actually stops an iCloud download mid-way isn't documented, so the design doesn't depend on it: a late result is dropped by the generation check. |
| Between load and encode | check `Task.isCancelled` before starting the encode, and skip it. |
| During JPEG encode | `Task.detached` doesn't inherit cancellation, and `UIGraphicsImageRenderer` can't be interrupted; it takes under 1 s. Its result is dropped. |

A cancelled preparation sets no error message.

**Tests (pure, no UI).** `PhotoDraftTests` drives `prepare` with loaders controlled by continuations:

- the newest pick wins over a slower earlier pick;
- cancel keeps the previous photo and sets no error;
- cancel while nothing is prepared leaves nothing;
- a late result after cancel is ignored;
- a failed load keeps the previous photo and sets the error;
- a new pick clears an old error;
- `clearAfterEstimate` keeps a newer pick.


# 10. Cancelled requests (M4, Phase 10)

**Today.** `URLError(.cancelled)` becomes `APIError.transport(.cancelled)`, whose text is "The request was cancelled. Please try again." (so it isn't the misleading "Can't reach the server" text). It is shown as an error. A Swift `CancellationError` thrown before the request starts isn't a `URLError`, so it would escape `APIClient` untyped and show "The operation couldn't be completed…". In practice `URLSession` reports `URLError.cancelled`.

**What can be cancelled:**

- a `.task` load when you leave the tab (History and Dashboard);
- `.refreshable` when History swaps its list for a spinner (likely);
- a photo preparation (0.7, by the user).

The estimate is never cancelled: its task isn't tied to the view. It must stay that way, because a cancelled estimate may still have saved the meal.

**Recommended behavior.** Cancellation is never an error for the user.

- Add `APIError.isCancellation(_ error: Error) -> Bool`, true for `CancellationError` and for `.transport` with `URLError.cancelled`.
- The store and the views ignore such errors: state is unchanged and no message is shown.
- A user-initiated cancel (photo) shows nothing. The UI simply returns to the previous state.
- Keep the existing `.cancelled` description as a fallback (no UI path should reach it).

**Wording: none.** No new user-facing text.

# 11. `goal_adjusted`, BMR and TDEE (Phase 8)

**Backend (unchanged).** A formula goal of 0 or below becomes 2200 with `goal_adjusted: true`; positive goals are kept. `goal_adjusted` is returned only by `POST /users/onboarding`. It isn't stored and isn't in `/users/profile`.

**iOS today.** `OnboardingResult` doesn't decode `goal_adjusted`, and a test pins that (`onboardingResultIgnoresGoalAdjusted`). The results step shows the goal, "BMR" and "Maintenance" with no notice.

**Reachable from the app?** Yes. A sweep of every input the app allows (both sexes, age 13–120, 3'0"–8'11", 70–700 lb in 5 lb steps, 5 activity levels, 3 goals; 29.6 M combinations) through the real `calculate_daily_calorie_goal` found:

- **6,585 adjusted** combinations. Example: female, 120, 3'0", 70 lb, sedentary, lose weight → BMR 128, TDEE 154, goal **2200** (adjusted). The screen then shows "2200 / BMR 128 / Maintenance 154" with no explanation.
- **Minimum BMR is 128.** Negative BMR/TDEE **can't** come from the app's inputs; they need the backend's wider limits (for example 20.01 kg and 50.01 cm → BMR −248), which only a direct API call can send.
- **658,446 combinations give a positive goal under 1000 kcal, down to 1 kcal**, accepted without any notice. Example: the same person with "maintain" gets a goal of **154**. This is the undecided nutrition policy (0.4 D4). It is **not** fixed in 0.7 (see decision D4).

**Proposed 0.7 change (client only).**

- Decode `goal_adjusted` as `goalAdjusted` (`OnboardingResult`). A missing key decodes as false, so an older server still works.
- On the results step, when `goalAdjusted` is true, show a neutral notice under the goal: **"We couldn't calculate a calorie goal from these details, so we've used a default goal of 2,200 calories per day."** (2,200 is the goal returned in the response) The number comes from the response, not a constant. It doesn't mention editing later, because there's no Settings screen yet.
- Show the BMR / Maintenance cards **only when** `!goalAdjusted && bmr > 0 && tdee > 0`. Hiding them when adjusted avoids "2200 vs Maintenance 154". The `> 0` guard is defensive for API-only inputs.
- **Tied to the result, one-time:** shown on the results step only. A persistent notice needs a stored flag (the Phase 3 goals table `source`), so it's deferred.

**Problems:**

- two different weight floors (1 and 70);
- silent changes to what the user typed (the submit clamp rewrites the value on screen);
- `onChange` clamping fights typing (clearing the field snaps back);
- validation mixed into `submitOnboarding`, with no tests.

Any 422 shows "Some of the information sent wasn't valid."

**Classification:**

- *Structurally invalid:* empty or non-numeric weight, weight ≤ 0. Must be blocked.
- *Clearly impossible:* weight under 70 lb or over 700 lb for someone aged 13+; the current app range, which the backend sweep test (`ios-limits`) already relies on.
- *Extreme but possible:* age 120, 3'0", 700 lb. Allowed.
- *Nutrition policy:* a goal floor or ceiling, adult-only use, and goal-rate rules. **Not 0.7.**

**Proposed 0.7 change (keeps every current range; no policy):**

- Put the ranges in one place in `OnboardingViewModel` (`static let ageRange = 13...120`, `weightRangeLb = 70.0...700.0`, height feet and inches).
- Add `var weightError: String?`: "Enter a weight between 70 and 700 lb." when the value is outside the range.
- Remove the `onChange` clamp and the silent submit clamp. Continue on the Body Metrics step is disabled while `weightError != nil`, and the message shows under the field.
- Steppers already enforce their ranges. `submitOnboarding` refuses (sends no request) if anything is out of range, as a backstop.
- Inject `APIClient` (default `.shared`) so submit is testable.

**Tightening ranges** (for example 18+ or 4'0"+) is a product decision (D5), recommended **not** for 0.7.
