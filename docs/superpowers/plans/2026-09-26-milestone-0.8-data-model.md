# 3. Current architecture (inspected in code)

**Backend** (FastAPI, SQLAlchemy, Alembic, SQLite):

- `users`: profile columns plus `daily_calorie_goal INTEGER NOT NULL` with `CHECK (> 0)` (`0002`). The only goal storage; onboarding overwrites it, so there is no history.
- `meals`: typed totals, `confidence`, `calorie_low`/`calorie_high`, `created_at` (naive UTC), `local_date` (`0003`), and index `(user_id, local_date)`. **The user's text, the AI's `assumptions`, the model and the prompt are not stored.**
- `services/nutrition_ai.py`: `estimate_nutrition(...)` returns `NutritionEstimate`, which is the LLM output schema *and* the `POST /meals/estimate` response. The model comes from `config.OPENAI_MODEL`, with typed estimator errors.
- `services/meals.log_meal`: reads the clock before the estimate, then saves the meal (auto-save).
- `services/summary.get_daily_summary`: sums meals for a day and reads `user.daily_calorie_goal`.
- `get_current_user` (always user 1), and `get_request_timezone` (`X-Timezone`, 400 if invalid). Onboarding and profile don't read the timezone.
- Tests: the conftest uses a temporary database and refuses to run otherwise; a fake estimator; `test_contract.py` pins every response shape plus the fields the iOS app decodes, and every route's response model; `test_migrations.py` covers parity, pre-Alembic stamping, all-or-nothing revisions and per-revision round trips.

**iOS** (unchanged by this plan; its guarantees must hold):

- `NutritionStore` (`@MainActor @Observable`, owned by the app root): today's summary and meals, loaded together and applied all-or-nothing.
  - Refreshes that overlap share one store-owned task.
  - A `changes` counter drops refreshes that started before a log or delete.
  - `logMeal` returns once saved and refreshes in the background.
  - `deleteMeal` removes the row, then refetches.
  - Cancellation is never shown as an error.
- Error ownership: `loadError` (store); estimate, photo and delete errors stay in their views.
- Refresh triggers: first appearance, `scenePhase → .active`, pull-to-refresh, Retry, and after log and delete. No monitoring, no throttling.
- `PhotoDraft`: the newest pick wins, and Cancel is available while a photo is being prepared.
- Onboarding: ranges in one place, strict weight parse, the `goal_adjusted` notice, and BMR/TDEE hidden when adjusted.
- **API dependencies:** `/meals/estimate`, `/summary/daily`, `/meals/today`, `DELETE /meals/{id}`, `/users/profile`, `/users/onboarding`. Decoders ignore unknown keys (`mealIgnoresFieldsTheAppDoesNotShow`), and `goal_adjusted` is optional.

# 4. What the roadmap defines for Phase 3

Phase 3 covers:

- `/v1` and one error format;
- new meal fields: `source`, `description`, `ai_provider`, `ai_model`, `prompt_version`, `ai_payload`, `edited_at`, and a nullable image reference;
- a `daily_goals` table (migrate `users.daily_calorie_goal` into it, then drop the column);
- `GET /v1/days/{date}`, replacing the today-only endpoints;
- an `EstimateResult` boundary, with the LLM schema separate from the API schema.

Done-when: typed OpenAPI (**done**, 0.3); **"changing the goal today leaves yesterday's summary unchanged"**; the model changed through the environment (**done**, 0.3); every data access through `get_current_user` (**done**, 0.3).

**Why split it.** Doing all of Phase 3 at once means three or more migrations, a breaking API change and an iOS migration in one review. Every milestone since 0.3 has been deliberately narrow.

**Why the data model goes first:**

1. **Data is being lost now.** Every meal logged today throws away the user's text, the AI's assumptions and the model/prompt used, and every onboarding overwrites the goal.
2. **The day endpoint depends on it.** Built first, the day endpoint would serve today's goal for past days and change its meaning later.
3. **It can ship with no API or iOS change**, so it's low-risk and easy to verify (the contract tests stay untouched).

# 6. Scope

**Included:**

1. **Estimator provenance.**
   - `estimate_nutrition` returns `EstimateResult(estimate, provider, model, prompt_version)`.
   - `provider = "openai"`. `model` is read from `config.OPENAI_MODEL` at call time. `PROMPT_VERSION` is a constant in `nutrition_ai.py`.
2. **Meal provenance columns** (migration `0004`), all nullable:
   - `source`: `text` or `photo`, worked out by the server from whether an image was sent;
   - `description`: the submitted message, verbatim;
   - `ai_provider`, `ai_model`, `prompt_version`;
   - `ai_payload`: JSON of the full model output, including `assumptions`.

   The 12 existing meals stay NULL, meaning unknown.
3. **The `daily_goals` table** (migration `0005`):
   - columns `id`, `user_id` (FK), `effective_date`, `calories` with `CHECK (calories > 0)`, `source`, `created_at`;
   - `UNIQUE (user_id, effective_date)`;
   - a lossless backfill of each user's current goal.
4. **Goal reads and writes by date.**
   - Onboarding upserts the row for today in the request's timezone, with source `calculated` or `default` (the `goal_adjusted` case, now stored permanently).
   - The summary for day D uses the latest row with `effective_date <= D`, else the default 2200.
   - The profile's `daily_calorie_goal` is the latest row, else 2200.
5. **Drop `users.daily_calorie_goal`** (migration `0006`, its own revision). The downgrade rebuilds it from the latest row.
6. **README and roadmap updates**, including the 0.9 split.

**Compatibility guarantee:** every response body keeps its exact shape and meaning. `test_contract.py` must pass **with an empty diff**.

# 9. Architecture and design

- **Estimator.** `EstimateResult` is a small dataclass in `nutrition_ai.py`, not a new module. `log_meal` passes it to `create_meal`. The route still returns `result.estimate`, so the response model stays `NutritionEstimate`.
- **Goals.** `goal_for(db, user, day)` and `set_goal(db, user, day, calories, source)` go in `crud.py`, which already holds the queries. `get_daily_summary` calls `goal_for`, and `get_user_profile` uses the latest row.
- **Atomic onboarding.** The profile fields and the goal row are written in one commit.
- **Default goal.** `DEFAULT_DAILY_CALORIE_GOAL = 2200` stays the pre-onboarding value and the fallback.
- **Migrations.** They freeze their own logic, like `0002`, and don't import app models. `0005` reads `config.DEFAULT_TIMEZONE` only for users with no meals, as `0003` does.
- **Dropping the column.** `0006` uses `batch_alter_table`, which rebuilds `users`. Foreign-key enforcement is off on SQLAlchemy's SQLite connection, so the `meals → users` FK survives. A test with data covers this.
- **Portability.** `sa.JSON` works on SQLite and Postgres, with no SQLite-only features.
- **`ai_payload`** is `estimate.model_dump()`: model output only, never image bytes, and a test asserts this.
- **Keeping `prompt_version` honest.** One test pins a hash of the prompt text and instructions next to `PROMPT_VERSION`, so editing the prompt without bumping the version fails.

# 11. Database and API implications

- **Schema:** `0003 → 0004` (meals gain 6 nullable columns) `→ 0005` (`daily_goals` plus backfill) `→ 0006` (drop `users.daily_calorie_goal` and its `CHECK`; the positivity rule now lives on `daily_goals.calories`).
- **Expected real-database result:** 12 meals unchanged, with provenance NULL. One goal row: user 1, 2633, `migrated`, effective 2026-09-01. Today's summary goal and the profile goal stay 2633.
- **API:** every path, method, status and body is the same. The only behavior change is D7 (an invalid `X-Timezone` on onboarding gets a 400).
- **Downgrades are lossy by nature.**
  - `0006 → 0005` restores the column from the latest goal row.
  - `0005 → 0004` drops goal history.
  - `0004 → 0003` drops provenance captured since the upgrade.

  **The backup file, not the downgrade, is the real rollback.**
- **Mixed code and schema:** 0.7 code can't run against a `0006` database (no `users.daily_calorie_goal`). README gets a note alongside the existing pre-0.4 one.

  - Code: reset `main` to `4fdf7be`, only with your approval.

# 16. Risks and edge cases

| Risk / edge case | Mitigation |
|---|---|
| Dev-server auto-reload onto branch code against an unmigrated database | Worktree (D10); the stop → backup → fast-forward → migrate order after merge |
| `0006` rebuilds `users` on SQLite (FK from `meals`, `CHECK` removal) | Round-trip test with data; rehearsal on the real copy |
| Photo-only meals: the app sends "Estimate this meal from the image.", which is stored as `description` | Accepted; the client can send an empty message in 0.9 |
| Two onboardings at the same moment on the same day hit the unique constraint (500) | Single user; accepted and marked with a `ponytail:` comment (upgrade: `INSERT … ON CONFLICT`) |
| A meal logged just before midnight | The goal lookup uses the meal's `local_date`, so behavior is unchanged |
