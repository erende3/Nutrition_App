# 2. Why this milestone

"Saved meals must be editable; totals follow" is a core product promise, and meal editing is the one Phase 5 feature not blocked by the calorie-goal bounds. SQLite currently reuses the id of the newest meal after it is deleted (`meals.id` has no AUTOINCREMENT). That is harmless while clients never keep an id, but an edit sent with a reused id would silently rewrite a different meal, so identity is fixed first, in the same milestone.

# 4. Scope

1. **Migration `0007`:** rebuild `meals` with AUTOINCREMENT and a nullable `edited_at` (naive UTC, like `created_at`). All rows and ids preserved; indexes recreated; `sqlite_sequence` seeded to the current max id. Downgrade rebuilds without both.
2. **`PATCH /v1/meals/{id}`:** partial update of the E4 fields with E7 validation; sets `edited_at`; returns 200 and the meal; `404 meal_not_found` for a missing or other user's meal; `422 validation_failed` for an empty body, unknown or immutable fields, or out-of-range values.
3. **`MealResource`** gains `edited_at` (additive). E11 placeholder mapping in v1 only.
4. **iOS data:** `Meal` decodes the detail fields; `APIClient.updateMeal`; `NutritionStore.updateMeal`, routed to the meal's own day like delete.
5. **iOS UI:** Meal Detail and the Edit sheet as approved at the design checkpoint; History rows open the detail without breaking swipe-to-delete.
6. **Docs:** roadmap "Milestone 0.12" section; README API section.

**Out of scope:** section 9.
