**Existing tests.**

- `test_error_contract.py`: `{"detail": str}` for 400/404/413/500/502/503/504; list of `{msg}` for 422.

**iOS APIClient.** Six calls, all with `X-Timezone`: `POST /meals/estimate` (multipart, `meal.jpg`, `image/jpeg`, 300 s), `GET /summary/daily` + `GET /meals/today` (parallel, `NutritionStore`), `DELETE /meals/{id}`, `GET /users/profile`, `POST /users/onboarding` (JSON). Views read: result card `meal_name`, `calories`; Dashboard `calories_consumed`, `calories_remaining`, `daily_goal` (`percentage` unused); History name, calories, macros (`created_at` decoded, never parsed). Swift `Codable` ignores unknown keys: **adding fields never breaks the app; changing paths, removing/renaming required fields or changing the estimate response does.** Errors without `detail` fall back to "The server returned an error (N)".

**Error behaviour today: four shapes.**

- Our `HTTPException`s: `{"detail": str}`.
- FastAPI 422: `{"detail": [{type, loc, msg, input, ctx}]}` — echoes submitted input.
- Starlette 404/405: `{"detail": "Not Found"}` etc.
- Unhandled exceptions outside the estimate route: `text/plain` "Internal Server Error".

No machine-readable codes anywhere.

**Provenance (0.8).** Stored: `source`, `description`, `ai_provider`, `ai_model`, `prompt_version`, `ai_payload`. **None public.** Pre-0.8 meals are NULL. Photo-only meals store the app's placeholder "Estimate this meal from the image." as `description`.

**Goals (0.8).** `daily_goals` is internal. `/summary/daily` uses the goal effective that day; the profile shows the latest; onboarding returns the new goal. Goal `source` is never exposed; `goal_adjusted` only in the onboarding response.

# 2. Weaknesses and ambiguities

1. No versioning: any change breaks the installed build.
2. Four error shapes, no codes; clients would have to match message strings. 422 echoes user input; unhandled 500s are not JSON.
3. The estimate returns the LLM schema, not the saved meal: no id, and LLM/prompt schema changes leak into the API.
4. `created_at` has no offset and two formats (with/without fraction); UTC only by convention.
5. "Today" needs two requests (summary + meals) that can straddle a write. A past day has a meal list but no summary, though `goal_for` supports one.
6. Inconsistent naming: `/meals/date/{d}` vs `/summary/daily`.
7. Empty `message` → 422, so the client invents a placeholder that is stored as `description`.
8. Profile enum fields untyped (`str`) in OpenAPI.
9. Estimate POST returns 200 (not 201); DELETE bodies go unread; destructive `DELETE /meals/today` unused.
10. Profile "latest goal" can disagree with `goal_for(today)` across timezones (edge case).
11. Empty `X-Timezone` silently falls back to the server default.
12. OpenAPI documents no error responses.

# 3. Proposed API Contract v1

**Structure.** v1 is a mounted FastAPI sub-app: `app.mount("/v1", v1_app)`, with its own exception handlers (the envelope), `/v1/openapi.json` and `/v1/docs`. The legacy root app is unchanged, so the existing contract and error tests pass untouched (proof of compatibility), and the root OpenAPI tripwire doesn't fire (mounted routes aren't in the root schema). Simpler alternative: one prefixed router with path-checking handlers — slightly less code, but mixes both error shapes in one app.

**Shared errors.** A new `ApiError(HTTPException)` carries a `code`. Shared code (timezone dependency, image checks, estimate failures) raises it. Legacy routes render it through FastAPI's default handler as `{"detail": message}` — byte-identical to today, no legacy handler needed. v1 renders the envelope.

## Endpoints

| v1 | Replaces | Notes |
|----------------------|----------------------|--------|
| `GET /v1/days/{date}` | `/summary/daily`, `/meals/today`, `/meals/date/{d}` | new |
| `POST /v1/meals/estimate` → **201** `Meal` | `/meals/estimate` | returns the saved meal |
| `DELETE /v1/meals/{id}` → **204**, empty body | `/meals/{id}` | |
| `GET /v1/users/profile` | same | same shape (the legacy users router, mounted as is) |
| `POST /v1/users/onboarding` | same | same shape |

`DELETE /meals/today` and `GET /` have no v1 equivalent. `X-Timezone` stays optional on writes, with the documented server-default fallback.

## Day semantics

- `{date}` is a strict `YYYY-MM-DD`: **the user's calendar date on which a meal was logged** (`meals.local_date`, fixed at submit time from `X-Timezone`).
- Reading a day does no timezone maths; `X-Timezone` is ignored. The client computes "today" in its own timezone. A meal logged at 23:30 in New York stays on that date after the user travels.
- Goal: the latest `daily_goals` row effective on or before `{date}`; if none, the default 2200. The goal's source (`migrated` / `calculated` / `default`) stays internal (D7).
- Any valid date is allowed (empty meals). Invalid date → 422.

```json
GET /v1/days/2026-09-27
200
{
  "date": "2026-09-27",
  "goal": {"calories": 2633},
  "totals": {"calories": 1250, "protein_g": 80.5,
             "carbohydrates_g": 120.0, "fat_g": 40.2},
  "calories_remaining": 1383,
  "percentage": 47.5,
  "meals": [ Meal, ... ]
}
```

Meals newest first. `calories_remaining` and `percentage` keep the legacy `/summary/daily` semantics exactly: remaining = max(goal − consumed, 0); percentage = min(consumed / goal × 100, 100), rounded to 1 decimal (0.0 if the goal were not positive). They are computed by the same code as the legacy summary. Macro totals are sums of the day's meals, rounded to 1 decimal (so float noise like 80.50000001 never appears). `goal` is an object so Phase 5 macro targets can join it.

## Meal

```json
{
  "id": 17, "meal_name": "Chicken and rice", "calories": 650,
  "protein_g": 45.0, "carbohydrates_g": 70.0, "fat_g": 15.0,
  "confidence": 0.8, "calorie_low": 550, "calorie_high": 750,
  "assumptions": ["1 cup cooked rice"],
  "source": "text",
  "description": "chicken and rice",
  "local_date": "2026-09-27",
  "created_at": "2026-09-27T18:04:11Z"
}
```

- `created_at`: UTC with `Z`, whole seconds — one format.
- `assumptions` from `ai_payload`; `null` for pre-0.8 meals (which also have `null` `source` and `description`).
- **Internal:** `ai_provider`, `ai_model`, `prompt_version`, `ai_payload`, `user_id`.
- **Image reference:** no field now; added later (non-breaking). v1 documents "clients ignore unknown fields". No image bytes stored.
- In v1, `message` is optional when a photo is attached. The server passes the same placeholder text to the prompt (so `PROMPT_VERSION` is unchanged) and stores `description = NULL`.

## Error envelope

```json
{"error": {"code": "image_too_large",
           "message": "The photo is too large. Please choose a smaller photo."}}

{"error": {"code": "validation_failed",
           "message": "Some of the information sent wasn't valid.",
           "fields": [{"field": "body.age",
                       "message": "Input should be greater than or equal to 13"}]}}
```

Codes are stable snake_case, never renamed; messages are safe to display and may change. `fields` appears only on `validation_failed`, never echoing `input` or `ctx`.

| Status | Code |
|---|---|
| 400 | `invalid_timezone`, `unsupported_image_type`, `empty_image`, `invalid_image` |
| 404 | `meal_not_found`, `not_found` (unknown route) |
| 405 | `method_not_allowed` |
| 413 | `image_too_large` |
| 422 | `validation_failed` (body, path, bad JSON, v1 estimate with neither text nor photo) |
| 500 | `internal_error` — any unhandled exception, always JSON, never exception text |
| 502 / 503 / 504 | `estimation_failed` / `estimation_unavailable` / `estimation_timeout` |

## Goals

No public goal-history endpoint; `daily_goals` stays internal. The 0.8 historical behaviour is kept and visible per day via `/v1/days/{date}`. The profile keeps `daily_calorie_goal` as the current goal. No calorie bounds are introduced.

**No database change or migration.** Everything derives from existing columns; Alembic head stays `0006`.

# 5. Acceptance tests

## Automated (backend, temporary test DB only)

- Exact shapes of every v1 response incl. nullability; `created_at` matches `…Z`; internal fields absent (set equality); a v1 OpenAPI operation map as a second tripwire.
- The 201 estimate response equals the same meal from `GET /v1/days/{its local_date}`.
- Day endpoint: macro and calorie totals; only that date, newest first; historical goal (change today, yesterday unchanged); default goal 2200 with `goal` exactly `{calories}`; parity with legacy `/summary/daily` (see section 6); same result under different `X-Timezone`; legacy NULL-provenance meal gives nulls; invalid date → `validation_failed`.
- Every code/status pair above, parametrized: no `input` echo on 422; forced exception in a non-estimate route → JSON `internal_error` without exception text; unknown `/v1` path → `not_found`; wrong method → `method_not_allowed`.
- DELETE: 204 empty; repeat → 404 `meal_not_found`; another user's meal → 404.
- Photo with blank message saves with `description` NULL and the estimator gets the placeholder; blank text without photo → 422.
- `test_contract.py` and `test_error_contract.py` pass **unchanged**.

## Physical iPhone acceptance (final gate before merge)

1. **Old installed build** against the branch server: Dashboard, log, History, delete all still work (legacy intact).
2. Install the new build: Dashboard goal 2633, consumed and remaining match what the old build showed.
3. Log a text meal: result card appears; Dashboard and History update.
4. Photo-only meal with empty text: saves; a **read-only** `sqlite3 -readonly` check shows `description` NULL.
5. Delete a meal: totals update.
6. Server without the OpenAI key (`env -u`): phone shows "Meal estimation is not available right now." Server stopped: transport message.
7. Phone set to a timezone whose date differs from the Mac's: Dashboard shows the phone's day; a new meal lands on it.
8. Background across midnight (or timezone change), foreground: new day shown.
9. Network switch then Retry still recovers.

Onboarding checked in the simulator against a scratch DB only.

## Test re-evaluation for D7

- `goal` is pinned with **set equality** to exactly `{"calories": int}`: a `source` key (or any other) fails the test.
- `percentage` is pinned as a JSON number, and **parity** tests assert that `/v1/days/{today}` and legacy `/summary/daily` return identical `calories_remaining` and `percentage` (and `goal.calories` = `daily_goal`, `totals.calories` = `calories_consumed`) for: no meals, a partial day, an over-goal day (100 cap, remaining 0), and a fractional value (1-decimal rounding).
- Historical goal: after a goal change today, yesterday's `goal.calories` and `percentage` use yesterday's goal.
- No goal history: `goal.calories` = 2200.
