**API architecture.** `app.py` serves the frozen unversioned routes (`/meals/estimate`, `/meals/today`, `DELETE /meals/today`, `DELETE /meals/{id}`, `/meals/date/{d}`, `/summary/daily`, `/users/profile`, `/users/onboarding`) with `{"detail"}` errors, and mounts a separate FastAPI app at `/v1` (`api_v1.py`): `GET /v1/days/{date}`, `POST /v1/meals/estimate` (201, saved `MealResource`), `DELETE /v1/meals/{id}` (204), and the users router mounted unchanged. v1 errors use `{"error": {code, message[, fields]}}`; `ApiError` keeps legacy bodies byte-identical. Provenance (`ai_provider`, `ai_model`, `prompt_version`, `ai_payload`) and goal `source` are internal.

**iOS architecture.** SwiftUI, iOS 18.5 minimum. `APIClient` calls **only `/v1`**; `NutritionStore` (`@Observable`) holds one `Day` per refresh; Dashboard (`ContentView.swift`) and History (`MealHistoryView.swift`) read it; `RootView` gates onboarding on the profile. The iOS `Meal` struct does not decode `description`, `source` or `assumptions`. Styling is ad hoc: hardcoded `Color(red: 0.04…)` backgrounds, `.white`/`.gray` text, fixed font sizes (36, 46, 56, 72 pt) that ignore Dynamic Type, **`.preferredColorScheme(.dark)` on the Dashboard only** (History follows the system setting, so light-mode phones get a dark Dashboard and a light History), and no accessibility modifiers anywhere.

**Roadmap position.** Phases 0–3 are complete (0.9 closed Phase 3). The roadmap's next phase is **Phase 4: Design system foundation (UI UX Pro Max)**, which depends on Phases 2 and 3 (both done). Phase 5 (core tracking: edit, calendar History, macro targets, Settings) depends on Phase 4 and on the still-open calorie-goal bounds decision. Phase 7 (AI evals) may run in parallel after Phase 3.

# 2. The two deferred 0.9 items

**Item 1: placeholder description on historical photo meals.** Verified read-only: **zero rows are affected in the real DB** (all 12 meals are pre-0.8, `source` and `description` NULL). The only producer is the legacy `POST /meals/estimate` called by a pre-0.9 app build; the installed iPhone build uses `/v1` (0.9 acceptance step 2). The iOS app does not decode `description`, so nothing user-visible depends on it.
**Decision D6: deferred, not fixed in 0.10.** It belongs with whichever comes first: retiring the legacy routes (removes the only producer) or Phase 5's meal detail (first screen to show `description`). When fixed: a read-time mapping in `meal_resource` for `source == "photo"` and the exact placeholder, plus a write-time guard in the legacy route; never a data rewrite.

**Item 2: `python app.py` fails in a worktree without `backend/.venv`.** Reproduced in isolation: uvicorn 0.51 `Config(reload=True, reload_excludes=["/nonexistent/.venv"])` raises `NotImplementedError: Non-relative patterns are unsupported`; with an existing directory it works.
**Decision D5: fixed in 0.10, as its own isolated commit.** It is dev tooling, not served behavior; every milestone uses a worktree; the fix is about three lines (`reload_excludes` only when the directory exists — a worktree run uses the main `.venv`, which is outside the watched tree anyway) plus one test. It removes the manual workaround from future acceptance runs.

# 3. Recommended scope

**Primary goal:** establish the app's visual foundation — semantic design tokens, a small set of reusable SwiftUI components, and an accessibility baseline — and move the **existing** screens (Root, Onboarding, Dashboard, History) onto them, with **no change to data, API, networking or product behavior**.

**Why this is the correct next milestone.**

- It is the roadmap's next phase; its dependencies (stable client state, v1 contract) are now met.
- Phase 5 builds new screens (calendar History, meal detail/edit, Settings, macro progress). Building them on today's hardcoded styling would mean restyling them again; the roadmap puts design first to avoid that rework.
- It does not require the undecided calorie-bounds policy (Phase 5 does), so it makes progress without inventing product policy.
- It fixes real present defects: the half-dark/half-light color-scheme split, text that ignores Dynamic Type, and an unlabeled calorie ring for VoiceOver.
- It is reviewable as one milestone: iOS-only, no backend runtime change, no API or schema change.

**Considered and not recommended as 0.10:** retiring the legacy routes (they are frozen, tested, cost nothing to keep, and removal is irreversible for any old build; roadmap decision 10 ties `/v1` to "before the first external build", so retirement fits Phase 8 or a later close-out); Phase 7 evals (parallel track, useful but not blocking the product path).

**In scope**

1. A design direction chosen with UI UX Pro Max, presented for your approval **before** any Swift changes (palette, type scale, spacing, radii, light/dark treatment), as a short visual artifact.
2. Tokens: semantic colors in the asset catalog (light and dark variants), a type scale built on Dynamic Type text styles, spacing and corner-radius constants.
3. Components used by today's screens only: card surface, primary and secondary buttons, `CalorieRing`, `StatCard`, meal row, load-error banner, and the loading/empty/error state views. Each has a SwiftUI `#Preview` (light, dark, largest accessibility text size).
4. Existing screens restyled onto the components, with identical behavior.
5. Accessibility baseline: VoiceOver labels/values (ring reads e.g. "1,250 of 2,633 calories, 1,383 left"), grouped stat cards, Dynamic Type through accessibility sizes without truncating numbers, WCAG AA contrast for text, Reduce Motion respected by the ring animation, 44 pt touch targets.
6. Item 2 fix (isolated commit), and the roadmap updated to record 0.10 and both 0.9 deferrals.

**Out of scope:** new screens or features, macro display, any data or API change (section 7).
