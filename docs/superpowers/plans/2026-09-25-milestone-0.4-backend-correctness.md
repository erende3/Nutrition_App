# 2. Current project assessment

**What's solid:**

- The core loop (text or photo estimate, auto-save, totals, History, delete) works on a physical device.
- The backend is layered into routes, services, CRUD, dependencies and config.
- Every route has a typed response.
- Errors are safe.
- There are 72 tests, including contract tests pinning every field iOS decodes, and a guard stops tests from reaching the network.
- Onboarding persists correctly across relaunches.

**What's still wrong (the Phase 1 bugs):**

1. **Meals logged in the evening vanish from "today."**
   - `created_at` is stored as naive UTC (`models.py`, `default=datetime.utcnow`), but "today" is the server's *local* date (`crud.get_todays_meals` -> `date.today()`), and the comparison is `created_at.date() == today` (`crud.py:43-59`).
   - In US Eastern time, a meal logged after 8:00 PM EDT (7:00 PM EST) is stamped with the *next* UTC day. It drops out of today's list and totals, and counts toward tomorrow.
   - This is a real, visible bug on your phone today, pinned by `test_late_evening_meal_counts_toward_that_local_day` (xfail, `0 == 300`).
2. **Extreme but accepted onboarding inputs produce a negative calorie goal.** The service stores and serves whatever Mifflin-St Jeor plus the goal adjustment yields:
   - `-779` at the backend's own input limits;
   - `-346` at the limits the iOS app allows (3 ft 0 in, 70 lb, age 120, female, sedentary, lose weight).

   Pinned by two xfails.
3. **There's no migration path.** The schema is created with `Base.metadata.create_all` when the app is imported (`app.py:23`). Any column or constraint change, which fixes 1 and 2 both need, can't be applied to an existing database such as your device-test `nutrition.db` without a migration tool.

**Smaller facts that shape the plan:**

- iOS decodes `created_at` as a `String` and never parses or displays it, so its format is not user-visible.
- iOS sends no timezone information. Every request function in `NutritionAPI.swift` builds its own request, and three use `URLSession.data(from:)` with no request object at all. Adding a header therefore means touching 6 functions, which is the Phase 2 `APIClient` work.
- The dev server and the iPhone are in the same timezone (US Eastern), so a server-timezone fallback gives correct days in your setup even before iOS sends a header.
- `get_meals_by_date` filters in Python after loading every meal the user has (O1, deferred from 0.3). A `local_date` column lets this become an indexed SQL filter at no extra cost.
- Milestone 0.3 left 5 Minor findings. Only one touches code this milestone changes: blank values for settings crash `config.py` (Minor 4), and 0.4 adds settings to that same module.

# 4. Scope

**In scope:**

1. **Alembic.**
   - Add the dependency.
   - A baseline revision equal to today's schema.
   - `nutrition.db` gets "stamped" at the baseline, which records its current schema version without changing any tables.
   - The schema is created or updated only by migrations, not by `create_all` when the app is imported.
2. **The calorie-goal invariant (not nutrition policy).**
   - A stored goal is always a positive integer. When the formula yields 0 or below, onboarding stores the app's existing default goal (2200, the value every user already has before onboarding) and reports `goal_adjusted: true` (D4, option B).
   - An additive `goal_adjusted` field in the onboarding response.
   - A database `CHECK (daily_calorie_goal > 0)`.
   - A summary guard, so an invalid stored goal can't cause a failure.
   - **No nutrition-policy bounds:** no recommended minimum or maximum and no sex-specific floors. Those are deferred as a product decision.
3. **Day correctness.**
   - A `local_date` column on meals, backfilled for existing rows.
   - The request timezone comes from an optional `X-Timezone` header (an IANA name), falling back to a configurable server default.
   - "Today" is computed in that timezone.
   - `/meals/today`, `DELETE /meals/today`, `/summary/daily` and `/meals/date/{d}` filter by `(user_id, local_date)` in SQL, with an index.
   - A clock seam so tests can freeze "now".
4. **One piece of 0.3 debt:** settings tolerate blank values (Minor 4), because this milestone adds settings to the same module.
5. **Docs:** README (the migration command and the new settings), `.env.example`, and a roadmap note.

**Not changed in 0.4:** API paths, response field names, the `created_at` value and format, iOS code, upload handling, and the error body shape.

## Migration execution safety

**Confirmations:**

1. **Migrations never run because a module was imported.**
   - The only automatic call is inside `app.py`'s `if __name__ == "__main__":` block, before `uvicorn.run`. Importing `app`, `database`, `models` or anything else runs no migration, and after T1 importing also creates no tables.
   - With `reload=True`, uvicorn's reloaded worker processes import `app:app` as a module, so they never migrate either. The migration runs once, in the process you started.
   - Tests use `create_all` on temporary databases (D11) and never touch Alembic, except in `test_migrations.py`, which calls it explicitly on temporary databases.
2. **If the automatic migration fails, startup fails clearly.** The planned `__main__` flow is:
   1. Run `alembic upgrade head`. Any exception propagates, so the process prints the traceback and exits non-zero **before** `uvicorn.run` is called.
   2. Then, as a second guard, compare the database's current revision with the script head. If they differ, exit non-zero with a message naming both revisions and the command to fix it.
   3. Only then start uvicorn.
3. **No half-migrated schema.**
   - `env.py` sets `transaction_per_migration=True`.
   - SQLite executes DDL inside transactions, and Python's `sqlite3` driver (3.6 and later) no longer auto-commits before DDL. So a revision that fails partway rolls back to the previous revision, including batch-mode table rebuilds.
   - T1 verifies this rather than assuming it (tests below).
4. **Running uvicorn directly** (`uvicorn app:app ...`) doesn't auto-migrate, by D3. The README tells you to run `alembic upgrade head` first. Guarding that path too (a startup check that refuses to serve when the database isn't at head) is possible, but it would also fire under `TestClient`, whose test databases aren't versioned. It isn't planned; say if you want it.

**Tests added in T1:**

- Importing `app` on a fresh database creates no tables and no `alembic_version` table.
- Running the `python app.py` startup path with a deliberately failing migration (a temporary script directory holding a broken revision) exits non-zero, and uvicorn is never started (`uvicorn.run` is patched to record calls).
- A revision that fails after its first DDL statement leaves the database at the previous revision, with no partial column or table.
- The revision check exits non-zero when the database is behind head.

# 16. D4 revisited: software invariant vs nutrition policy

**The two concerns:**

- **The software/data invariant** is required now. A stored daily goal is always above 0, the database enforces it, and the summary can't fail on an invalid stored value. This is what the two strict xfails test: `status_code == 200` and `goal > 0`.
- **Nutrition policy** is a product decision and can wait. It covers the minimum and maximum goals MyNutritionPal should recommend, whether they differ by sex, and what to do with results that are positive but unrealistic. Your earlier notes say production thresholds are undecided and 1200/1500 are placeholders.
