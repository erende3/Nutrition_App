# Milestone 0.3: Backend/API Architecture Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (approved: native execution) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the backend clear route → service → data boundaries, typed response models for every route, a hardened and configurable AI service with safe error handling, and one current-user seam, without changing anything the iOS app can see.

**Architecture:** Contract tests pin every response first. Then:

1. A `config.py` settings module.
2. The nutrition AI service gains a cached client, an explicit timeout and retry count, a configurable model, and typed errors.
3. Meal logging and the daily summary move into `services/`.
4. The estimate route maps service errors to status codes with generic messages.
5. Every route declares a Pydantic response model.
6. All user-scoped routes resolve the user through `get_current_user`.

**Tech Stack:** Python 3.11, FastAPI 0.139, SQLAlchemy 2.0, Pydantic 2.13, openai 2.45, pytest 8.4, pyflakes 4.0.0.

**Spec:** the Milestone 0.3 plan (review artifact `docs/reviews/milestone-0.3-plan.pdf`, not committed), approved on 2026-09-25 with decisions D1–D8, and `docs/superpowers/plans/2026-09-24-mynutritionpal-roadmap.md`.

## Approved decisions

- **D1:** 0.3 is the behavior-preserving structural slice pulled forward from roadmap Phases 1 and 3, plus the unfinished Phase 0 model configuration. The roadmap is annotated.
- **D2:** estimate errors map to 503 (estimator not configured), 504 (AI timeout), 502 (AI or upstream failure) and 500 (unexpected). The body stays `{"detail": str}`, and exception text never reaches the client.
- **D3:** `/meals/today` and `/meals/date` share `MealResponse`, which has today's 7 fields plus `confidence`, `calorie_low` and `calorie_high`. It has no `user_id`.
- **D4:** `OPENAI_TIMEOUT_SECONDS=60` and `OPENAI_MAX_RETRIES=1` by default, both configurable through the environment.
- **D5:** `get_current_user` is added now and still returns the development user (id 1).
- **D6:** O2 (the first-user creation race fix, with a deterministic test) is included. O1 and O4 are deferred to Phase 1. O3 is skipped.
- **D7:** the synchronous OpenAI SDK keeps running through `run_in_threadpool`. No `AsyncOpenAI`.
- **D8:** `DELETE /meals/today` stays and gets a typed response model.
- **Contract tests** pin field sets, required fields, JSON value types, datetime format, the fields the Swift models need, and newest-first ordering. **JSON object key order is not part of the contract.**

## Global Constraints

- No user-visible iOS change and no Swift change. `frontend/MyNutritionPal/MyNutritionPal/NutritionAPI.swift` carries an intentional uncommitted `baseURL` edit that must never be staged or committed.
- Stage explicit paths only. Never use `git add .`, `git add -A` or `git commit -a`. Before every commit, `git diff --cached --name-only` must contain no `frontend/` path.
- The 3 known bugs stay pinned as `xfail(strict=True)` and must fail at their original assertions: `0 == 300`, `-779 > 0` and `-346 > 0`. Do not fix them.
- Out of scope:
  - timezone / `local_date`;
  - calorie goal clamping;
  - Alembic;
  - upload size limits;
  - `/v1`;
  - a day endpoint;
  - auth and Postgres;
  - rate limiting;
  - HealthKit and speech;
  - macro targets;
  - meal editing;
  - the History calendar;
  - idempotency keys;
  - `AsyncOpenAI`;
  - iOS changes.
- `backend/nutrition.db` must not be modified (baseline sha1 `0410c504b556c17b0b597bc698431f01d4ffe8bd`).
- `graphify-out/` and `docs/reviews/` are never committed.
- Work on `milestone-0.3-backend-architecture`, one logical change per commit, and never push or merge.
- Tests never reach the network. An autouse guard makes constructing a real OpenAI client fail.
- Run the suite after every task: from `backend/`, `.venv/bin/python -m pytest -q -p no:warnings`.

## Review Focus

1. **Contract drift.** Only two changes are intended:
   - `/meals/date` drops `user_id` and gains a declared schema;
   - estimate error statuses and detail text change.

   Everything else, including every field the Swift models decode, must serialize the same values and types.
2. **No leaked exception text.** Every estimate failure path returns a generic `detail` and logs the exception on the server.
3. **No event-loop blocking.** The estimator and the meal save both run in the thread pool.
4. **No network in tests.** Constructing a real OpenAI client fails in tests.
5. **Seam completeness.** No route calls `get_or_create_default_user` directly; every user-scoped route respects a `get_current_user` override.
6. **The race fix.** A concurrent first-user insert results in exactly one user 1 and no error.

### Task 3: Harden the nutrition AI service

- [ ] Conftest guard (autouse):

- [ ] Tests first. They install a fake `openai.OpenAI` that records its constructor kwargs and `responses.parse` kwargs, then check that:

  6. `openai.APITimeoutError` raises `EstimatorTimeout`.
  7. `APIConnectionError`, `RateLimitError`, `APIStatusError(500)` and a Pydantic `ValidationError` each raise `EstimatorFailed`.

  - `_client()`, an `lru_cache(maxsize=1)` function that does the lazy `from openai import OpenAI` and builds the client from the key and the config timeout and retries;
