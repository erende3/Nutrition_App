# 1. Executive summary

**Recommendation.** Milestone 0.6 should be the **photo pipeline**:

- The app downscales every meal photo to at most 1536 px on the long edge, re-encodes it as JPEG at 0.7 quality, and does this off the main thread.
- It stops crashing when there is no camera.
- It lets the user pick a photo from the library with `PhotosPicker`.
- The backend rejects images over a configurable size limit (default 10 MiB) with a `413` that the existing 0.5 error path already shows.

This closes the last open Phase 1 item (item 6, the upload limit) and the photo part of Phase 2.

**Why this, and why now.**

1. It's the dependency the roadmap and both previous plans named. 0.4 deferred the upload limit until downscaling existed, and 0.5 deferred downscaling to "0.6, photo pipeline". The 0.5 client can now show a 413 message, which was the last prerequisite.
2. Inspection found a real defect that the roadmap only hinted at. `CameraPicker` sets `sourceType = .camera` unconditionally, and `UIImagePickerController` raises an exception when that source isn't available. Tapping **Take Photo** on the simulator (or on any device without a usable camera) crashes the app. Phase 2's "Done when" requires "the app runs on a simulator with no camera".
3. The upload path has no bound at either end:
   - The client encodes the full-resolution image (about 2–5 MB) on the main thread when Estimate is tapped.
   - The server reads any upload fully into memory (`await image.read()`, `routes/meals.py:88`) and only trusts the client's declared content type.
4. It's small, self-contained and low-risk: **no schema change, no migration, no new endpoint, and no response-shape change.** It's the last "stabilization" item before the client-state milestone (0.7) and the Phase 3 contract work.

**Size.** About 7 focused commits. It's mostly iOS (one new file, one view reworked), plus a small backend change (one setting and bounded, validated reads in one route). About 15 new backend tests and 11 new iOS tests.

**Branch:** `milestone-0.6-photo-pipeline` (not created).

**The network-switch observation from 0.5** stays deferred to 0.7 (client state and loading/recovery). 0.6 adds one *diagnostic* acceptance step so 0.7 knows whether the cause is the UI (the Dashboard has no refresh trigger) or the networking stack.

# 9. Recommended Milestone 0.6 objective

> **A meal photo from the camera or the photo library reaches the backend as a small, upright, metadata-free JPEG prepared off the main thread; the app never crashes for lack of a camera; and the backend refuses oversized or non-image uploads with a clear message instead of forwarding them to the AI provider.**

Measurable outcomes:

1. A 12 MP camera photo uploads as ≤ 1536 px on the long edge, typically a few hundred KB (acceptance bar ≤ 750,000 bytes).
2. No image encoding happens on the main thread.
3. The app runs on a simulator with no camera, with the photo library available.
4. `POST /meals/estimate` returns `413` above `MAX_IMAGE_BYTES` (default 10 MiB) and `400` for bytes that aren't the declared image type, and saves nothing in either case.
5. No schema, response-shape, or endpoint change. The suites stay green.

# 10. Why this should be the next milestone

1. **It's the named dependency.** 0.4 said the limit waits for downscaling. 0.5 said downscaling waits for a client that can show server errors, and 0.5 built that. Nothing else blocks it.
2. **It fixes a crash (I1)** and removes a main-thread stall (I3). These are the only user-facing defects found in this inspection outside the planned 0.7 state work.
3. **It closes Phase 1 completely** and finishes the photo part of Phase 2. The remaining Phase 2 work (0.7) is then pure client state and UX.
4. **It's the right size.** One new Swift file, one reworked view section, one backend setting and one route change. It's a different risk profile from 0.7, which touches every view, so it deserves its own review.
5. **It's cheaper before Phase 3/4.** Phase 3 adds the image-reference and `source` fields, and Phase 4 restyles the logging UI. Both are simpler once the photo flow has one clean entry point: two sources feeding one `PreparedPhoto`.

# 11. Exact in-scope work

1. **Client downscaling.** A new `MealPhoto` utility:
   - long edge ≤ 1536 px, aspect ratio kept, never upscaled;
   - output drawn at scale 1 (pixels), upright (EXIF orientation applied), JPEG quality 0.7;
   - no source metadata, so no GPS.
2. **Off-main preparation.**
   - The photo is prepared right after it's picked, in a detached task.
   - The view holds only the small JPEG plus a preview decoded from it.
   - A progress indicator shows while preparing, and Estimate is disabled until the photo is ready.
   - A generation counter makes the newest pick win.
3. **Camera availability.** "Take Photo" is shown only when `UIImagePickerController.isSourceTypeAvailable(.camera)` is true.
4. **Photo library.**
   - A `PhotosPicker(selection:matching: .images)` button, "Choose Photo".
   - It loads `Data` through `loadTransferable`, then `UIImage(data:)` (HEIC, JPEG and PNG all work), then the same `MealPhoto` path.
   - A load failure shows "Couldn't load that photo. Try another one."
5. **Backend upload limit.**
   - A `MAX_IMAGE_BYTES` setting (default 10,485,760; must be positive).
   - A bounded read (`await image.read(MAX_IMAGE_BYTES + 1)`).
   - `413` with `{"detail": "The photo is too large. Please choose a smaller photo."}`.
   - The estimator is never called and nothing is saved.
6. **Backend content check (D4).** The bytes must start with the signature of the declared type (JPEG `FF D8 FF`; PNG `89 50 4E 47 0D 0A 1A 0A`; WebP `RIFF…WEBP`). Otherwise the response is `400` "The image isn't a valid JPEG, PNG, or WebP file."
7. **Tests** as specified in §24.
8. **Docs:**
   - README: the photo section, the new setting in the Configuration table, a simulator note;
   - `.env.example`;
   - roadmap: a Milestone 0.6 section, Phase 1 item 6 marked done, and the reconciliation annotations from §8.3;
   - the plan as `docs/superpowers/plans/2026-09-25-milestone-0.6-photo-pipeline.md`.

**The network-switch observation (question 12).**

- **What's known:** after the Mac and iPhone switched Wi-Fi, the running app didn't reconnect by itself, and a force-quit and relaunch fixed it.
- **Two plausible causes:**
  - (a) *UI*: the Dashboard fetches only in its first `.task` and has no Retry or pull-to-refresh (I6), so nothing re-requests after the failure;
  - (b) *stack*: stale keep-alive connections or a cached `.local` resolution in `URLSession.shared`.
- **Why it isn't in 0.6:** the fix for (a) is the 0.7 state/recovery work, and (b) needs evidence first.
- **What 0.6 does:** one diagnostic acceptance step (§26, step 16). After a network switch, does **History → Retry** recover without a relaunch?
  - If yes, the cause is (a) and 0.7's plan covers it.
  - If no, 0.7 must also look at the session or connection layer.
- Either way, nothing ships in 0.6 for it.

## 13.2 iOS: `MealPhoto.swift` (new, app target)

```swift
import UIKit

/// Meal photos as uploaded: at most 1536 px on the long edge, upright,
/// JPEG at 0.7, without the original's metadata (so no location).
enum MealPhoto {
    static let maxPixelLength: CGFloat = 1536
    static let jpegQuality: CGFloat = 0.7

    /// Long edge capped at maxLength, aspect kept, never upscaled, never 0.
    static func targetSize(for size: CGSize,
                           maxLength: CGFloat = maxPixelLength) -> CGSize {
        let scale = min(1, maxLength / max(size.width, size.height))
        return CGSize(width: max(1, (size.width * scale).rounded()),
                      height: max(1, (size.height * scale).rounded()))
    }

    /// Blocking; call off the main thread.
    static func uploadJPEG(from image: UIImage) -> Data? {
        let pixels = CGSize(width: image.size.width * image.scale,
                            height: image.size.height * image.scale)
        let size = targetSize(for: pixels)
        let format = UIGraphicsImageRendererFormat()
        format.scale = 1          // pixels, not points x screen scale
        format.opaque = true
        // ponytail: draws the fully decoded image; switch to ImageIO
        // thumbnailing if 48 MP library photos cause memory pressure.
        return UIGraphicsImageRenderer(size: size, format: format)
            .image { _ in image.draw(in: CGRect(origin: .zero, size: size)) }
            .jpegData(compressionQuality: jpegQuality)
    }
}
```

**Key points:**

- `UIImage.size` is already in *oriented* points, and `draw(in:)` applies the orientation, so a portrait camera photo (stored landscape with `.right`) comes out upright.
- `format.scale = 1` matters. The renderer's default scale is the screen's (3× on current iPhones), which would silently produce 4608 px images. There's a test for it.
- Re-encoding through the renderer drops EXIF and GPS. For library photos, **never** upload the original `Data`.

## 13.4 Backend

`config.py`:

```python
# Largest meal photo POST /meals/estimate accepts, in bytes.
MAX_IMAGE_BYTES = int(_setting("MAX_IMAGE_BYTES", str(10 * 1024 * 1024)))
if MAX_IMAGE_BYTES <= 0:
    raise ValueError("MAX_IMAGE_BYTES must be a positive number of bytes.")
```

`routes/meals.py`. Read the setting at request time (`import config as settings`, as `dependencies.py` does), so tests can monkeypatch it:

```python
IMAGE_SIGNATURES = {
    "image/jpeg": lambda b: b.startswith(b"\xff\xd8\xff"),
    "image/png": lambda b: b.startswith(b"\x89PNG\r\n\x1a\n"),
    "image/webp": lambda b: b[:4] == b"RIFF" and b[8:12] == b"WEBP",
}
...
if image.content_type not in IMAGE_SIGNATURES:          # 400, unchanged text
image_bytes = await image.read(settings.MAX_IMAGE_BYTES + 1)
if not image_bytes:                                      # 400, unchanged text
if len(image_bytes) > settings.MAX_IMAGE_BYTES:          # 413 (new)
if not IMAGE_SIGNATURES[image.content_type](image_bytes):  # 400 (new, D4)
```

The `allowed_types` set becomes the keys of `IMAGE_SIGNATURES`. There's no new module, dependency, or middleware. (Python's `imghdr` is deprecated and removed in 3.13, so it isn't used.)

## 24.1 Backend (about 15 new)

`test_meals.py`:

1. An image exactly at the limit is accepted. Monkeypatch `config.MAX_IMAGE_BYTES` to e.g. 64 and send 64 bytes starting with the JPEG signature: 200, and the estimator receives the exact bytes.
2. One byte over the limit returns **413** with the detail text. The estimator isn't called, `/meals/today` is empty, and the summary is unchanged.

## 24.2 iOS (about 11 new)

`MealPhotoTests` (new, not `.serialized`, pure):

1. `targetSize` for 4032×3024 is 1536×1152.
2. `targetSize` for 3024×4032 is 1152×1536.
3. 800×600 is unchanged (never upscaled).
4. Exactly 1536×1024 is unchanged (boundary).
5. A 12000×200 panorama gives 1536×26, and a 20000×1 strip never produces a 0 dimension.
6. `uploadJPEG` output starts with `FF D8 FF`, and its decoded pixel size is ≤ 1536 on the long edge with the aspect ratio kept. Decode it with `CGImageSourceCreateWithData`, reading pixel width and height.

8. **Orientation:** a landscape `CGImage` wrapped as `UIImage(cgImage:scale:1, orientation: .right)` produces a *portrait* output (height > width).
9. **Metadata:** a JPEG created with a GPS dictionary (via `CGImageDestination`), loaded with `UIImage(data:)` and processed, has no `kCGImagePropertyGPSDictionary` in its output properties.
10. A small image (e.g. 100×100) still yields valid JPEG data.
