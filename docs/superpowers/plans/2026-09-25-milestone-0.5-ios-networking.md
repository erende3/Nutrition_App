# Milestone 0.5: iOS networking foundation

**Date:** 2026-09-25
**Roadmap:** first slice of Phase 2 (iOS stabilization).
**Status:** approved 2026-09-25 with D1(a), D2(a), D3(a) (D3(b) only if the device test requires it), D4(a)–D10(a), D11 and D12.

> **For agentic workers:** implement task by task, test-first where a task says so. Keep the scope to section 4; everything in section 5 stays deferred.

# Recommendation in one paragraph

Milestone 0.5 should be the **iOS networking foundation**. It makes the backend address a build setting instead of a hardcoded IP. It sends every request through one `APIClient`, which adds `X-Timezone` and turns failures into plain-language messages using the backend's own `detail` text. It also gives the two dead-end error screens a Retry button. The backend gets no production code change; it gets one new contract test that pins the error body shapes the client will parse. **Image downscaling and the upload size limit are deliberately left to Milestone 0.6**, as a separate photo-pipeline milestone. Everything else on the deferred list stays deferred. About 7 small commits.

## 1.2 The iOS client today (the part 0.5 changes)

`NutritionAPI.swift` (193 lines) is a singleton with six methods. Each one copies the same four steps: build the URL, call `URLSession.shared`, check the 2xx status, decode with a fresh `JSONDecoder`.

| Finding | Where | Consequence |
|----------------|--------|----------------|
| Hardcoded `baseURL = "http://172.20.10.9:8000"` (Personal Hotspot IP) | `NutritionAPI.swift:14` | Every network change needs a source edit and rebuild. The IP is also committed (the pre-push audit flagged it as low risk). |
| Any non-2xx becomes `URLError(.badServerResponse)` and the body is discarded | all 6 methods | The backend's carefully generic messages ("Meal estimation timed out. Please try again.") never reach the user. They see "The operation couldn't be completed. (NSURLErrorDomain error -1011.)" |
| No `X-Timezone` header | all 6 methods | The server falls back to `DEFAULT_TIMEZONE`. That's correct only while the phone and the Mac share a timezone. |
| Only the estimate sets a timeout (300 s); the others use URLSession's 60 s default | `NutritionAPI.swift:28` | On the wrong network, a request to an unreachable LAN IP can spin for up to a minute before any error shows. |
| `RootView` error state has no retry | `RootView.swift:21-29` | If the profile load fails (e.g. the server isn't running yet, or the network changed), the only recovery is killing the app. |
| History error state has no retry | `MealHistoryView.swift:21-24` | `.refreshable` sits on the `List`, which isn't shown in the error state, so pull-to-refresh can't recover. |
| Dashboard never clears `errorMessage` after a successful refresh | `ContentView.swift:266-278` | A stale error stays on screen under fresh data. |
| `Info.plist` sets `NSAllowsArbitraryLoads = true` for **every** configuration | `Info.plist` | Release builds would also allow plain HTTP anywhere. |
| Models use snake_case property names; two use explicit `CodingKeys` | `Meal`, `DailySummary`, `NutritionEstimate` vs `UserProfile`, `OnboardingResult` | Works. Note: switching to `.convertFromSnakeCase` would **break** the explicit `CodingKeys` (`"height_cm"` would no longer match). See D7. |
| Photo: `jpegData(compressionQuality: 0.8)` of the full-resolution camera image, on the main thread; camera-only picker | `ContentView.swift:237`, `CameraPicker.swift:20` | It works today (roughly 2–5 MB per photo). It's the input to a future upload limit, which is 0.6's problem. |
| `OnboardingResult` ignores `goal_adjusted`; the results screen shows raw BMR/TDEE, which are negative for the extreme inputs that trigger the fallback | `OnboardingResult.swift`, `OnboardingView.swift:294-306` | A product/UI gap, not a networking one (see §5 and D9). |

## 1.3 Build configuration today

- There are no `.xcconfig` files. Debug and Release differ only in the Xcode defaults.
- The Xcode project uses file-system-synchronized groups (`objectVersion = 77`). Any file placed inside `MyNutritionPal/` joins the app target automatically, as a resource if it isn't a source file. Config files must therefore live **outside** that folder.
- `INFOPLIST_FILE = MyNutritionPal/Info.plist` plus `GENERATE_INFOPLIST_FILE = YES`. `NSLocalNetworkUsageDescription` and `NSCameraUsageDescription` are already set as build settings.
- The only scheme lives in `xcuserdata/` (ignored). `xcodebuild -list` still finds it on this machine.

# 2. Recommended milestone objective

> **The iOS app reaches the backend through one configurable, testable client that sends the device's timezone and tells the user in plain language what went wrong, and a developer can change networks without editing Swift source.**

Measurable outcome: no IP address in any tracked Swift file; every request carries `X-Timezone`; every failure shows a specific message, with a Retry where the screen would otherwise dead-end; networking has automated tests; the backend is untouched apart from one test.

# 3. Why this should be the next milestone

1. **The roadmap puts it next.** The 0.4 report lists three items moved to Phase 2: iOS `X-Timezone`, the `goal_adjusted` notice, and the configurable base URL. Phase 2's own dependency note says the base URL and `APIClient` work "can run alongside Phase 1". Phase 1 is now finished except for the upload limit, which is waiting on Phase 2.
2. **It completes 0.4's correctness work end to end.** 0.4 made the backend date meals by the client's timezone, but the client never sends it. Today the fallback only happens to be right because the phone and the Mac are both on Eastern time.
3. **Every later client milestone depends on it.** Image upload limits need a client that can show a 413 message. The shared store, the day endpoint, `/v1`, the error envelope and the auth header all change one `APIClient` instead of six copied methods.
4. **It removes the biggest day-to-day development friction.** The Mac's IP changes with each network (the 0.4 acceptance checklist had to warn that the Mac was on a different IP than the hardcoded one).
5. **It's low-risk.** No schema change, no API change, no change to the real database, and no change to what the AI sees. The riskiest part (the Xcode project file) is small and mechanical.

| D. Start Phase 3 (`/v1`, day endpoint, error envelope) first | Rejected. It changes the contract before the client can even parse today's errors, and the roadmap orders Phase 3 after Phase 2. |
| E. Backend polish (0.3/0.4 minors) | Rejected as a milestone. None of the remaining minors are user-visible; §5 schedules each one. |

## 3.2 Upload limit and image downscaling: deliberately deferred to 0.6

- **Hard dependency order:** the limit must come *after* downscaling. Otherwise a limit rejects real full-resolution photos (0.4's reason for deferring it). So both go together, and both go after the client can show server errors, which is 0.5.
- **Different risk:** 0.5 changes no request payloads. Downscaling changes the image the model estimates from. It deserves its own before/after check on real meals, and possibly an eval (Phase 7).
- **Different surface:** `CameraPicker`, `PhotosPicker`, camera-availability checks and off-main-thread encoding are UI and media work. None of them touch the networking seam beyond one `Data` argument.
- **Nothing breaks meanwhile:** current photos are about 2–5 MB and work end to end on the device.

# 4. Exact in-scope work

1. **Build-time base URL.**
   - `Config/Debug.xcconfig` and `Config/Release.xcconfig` (committed), plus `Config/Local.xcconfig.example` (committed). `Config/Local.xcconfig` holds the developer's value and is git-ignored.
   - `Info.plist` gets `APIBaseURL = $(API_BASE_URL)`.
   - A small `AppConfig` reads and validates the value.
   - The hardcoded IP is removed from Swift source.
2. **ATS narrowed:** replace `NSAllowsArbitraryLoads` with `NSAllowsLocalNetworking` (D3).
3. **`APIClient`:**
   - one generic request function over an injected `URLSession`, with `X-Timezone: TimeZone.current.identifier` on every request;
   - per-request timeouts (300 s for the estimate, 20 s for everything else);
   - no automatic retries;
   - the multipart body built by a pure function.
4. **`APIError`:**
   - The cases are `notConfigured`, `transport(URLError)`, `server(status:message:)` and `decoding`.
   - Parses `{"detail": str}`, maps a 422 list `detail` to a generic validation message, and falls back to a status-based message for a non-JSON body.
   - Conforms to `LocalizedError`, so existing `error.localizedDescription` call sites show the new text unchanged.
5. **Migrate all six calls** to `APIClient` and delete `NutritionAPI.swift`. The request and response models stay exactly as they are.
6. **Minimal recovery UX:**
   - a Retry button in the `RootView` and `MealHistoryView` error states;
   - the Dashboard clears `errorMessage` when a refresh succeeds;
   - the "can't connect" message names the server address it tried.
7. **Tests** (see §15–16):
   - iOS: `AppConfig`, the multipart builder, request building (including `X-Timezone`), error mapping, and decoding fixtures for every model.
   - Backend: one contract test file pinning the error body shapes.
8. **Docs:**
   - README iOS section (setup with `Local.xcconfig`, the `.local` hostname tip, `X-Timezone` now sent);
   - README "Days and timezones" (drop "The iOS app doesn't send the header yet");
   - roadmap Milestone 0.5 section;
   - the plan as `docs/superpowers/plans/2026-09-25-milestone-0.5-ios-networking.md`.

**Task 4. iOS: add `APIClient` and `APIError` (not yet used by the views).**

- `APIClient.swift`:

# 13. API compatibility implications

| Aspect | Effect |
|----------|------------------------------|
| Endpoints, paths, methods, bodies | Identical to today's client. |
| New request header | `X-Timezone: <TimeZone.current.identifier>` on all requests. Read by `/meals/today` (GET, DELETE), `/meals/estimate` and `/summary/daily`; ignored elsewhere. |
| Behavior change | "Today" follows the **phone's** timezone instead of the server's. With both on Eastern time, nothing visible changes. When they differ (travel, or a phone set manually), the phone wins, which is the intended 0.4 design. |
| New failure mode | If the phone's zone name were unknown to the server's tzdata, the 4 routes would return 400 with a clear message, now shown to the user. This is unlikely: iOS and macOS ship current tzdata. |
| Older app builds | Still work: the header is optional on the server. |
| Error parsing | The client depends on `detail` being a string (and a list for 422). Task 1 pins this, so a Phase 3 envelope change fails a test instead of silently degrading the messages. |
| Response decoding | Unchanged. Extra fields (`goal_adjusted`, `confidence`, and so on) are still ignored where not modeled. |

# 15. Configuration strategy

**Mechanism (D2):** the build setting `API_BASE_URL` → `Info.plist` key `APIBaseURL` → `AppConfig` → `APIClient`.

| File | Tracked | Contents |
|----------|------|--------------------|
| `Config/Debug.xcconfig` | Yes | `API_BASE_URL =` (empty default) then `#include? "Local.xcconfig"` (the `?` makes it optional, so a fresh clone still builds) |
| `Config/Local.xcconfig` | **No** (git-ignored) | The developer's value, e.g. `API_BASE_URL = http:/$()/Erics-MacBook-Pro.local:8000` |
| `Config/Local.xcconfig.example` | Yes | A template with instructions |
| `Config/Release.xcconfig` | Yes | `API_BASE_URL =` (empty until Phase 8) |

**Why the `.local` hostname:** the Mac's Bonjour name (`scutil --get LocalHostName`) is the same on home Wi-Fi and on the Personal Hotspot. The phone resolves it over mDNS, so changing networks needs **no rebuild**. The raw IP is the documented fallback for networks that block mDNS (some corporate or guest Wi-Fi). Whether mDNS resolves across the iPhone's own hotspot is verified in acceptance step 7. The raw IP is the fallback there too.

**Behavior when unset:** the app launches and the Root screen says no server address is set, and how to fix it. Nothing crashes, and no default IP is baked in.

**The xcconfig `//` gotcha:** in xcconfig, `//` starts a comment, so `http://host` becomes `http:`. The example file uses `http:/$()/host`. `AppConfig` rejects a URL with no host, so a mistake is caught at launch with a clear message.

**Alternatives rejected:**

- The IP committed in the xcconfig: it leaks the network again and forces a commit on every change.
- An in-app server setting: extra UI and persistence. The `.local` name makes it unnecessary; reconsider only if acceptance shows mDNS is unreliable.
- A launch-argument override: yet another config source.

# 16. Testing strategy and new automated tests

**Principles:**

- Test logic in pure functions where possible (the multipart builder, error mapping, URL validation).
- Test the request/response path through a `URLProtocol` stub injected via `URLSessionConfiguration.ephemeral.protocolClasses`.
- No test touches the network or a real server.
- The backend suite stays green and unchanged apart from Task 1.

# 19. Risks and likely failure modes

| Risk | Likelihood | Mitigation |
|--------------|------|------------|
| Hand-editing `project.pbxproj` corrupts the project | Medium | The edit is tiny (or done through Xcode's Project > Info > Configurations UI). Verify with `xcodebuild -list`, `-showBuildSettings` for both configurations, and a clean build. Its commit contains only config changes, so it's easy to revert. |
| The xcconfig `//` comment truncates the URL | High, for anyone new | The `$()` trick is in the example; `AppConfig` rejects `http:` with a clear message; a test covers it. |
| Placing xcconfigs inside the synchronized `MyNutritionPal/` folder bundles `Local.xcconfig` into the app | Medium | Keep `Config/` beside the `.xcodeproj`, not inside the synced group. Check that the built `.app` has no `.xcconfig`. |
| `NSAllowsLocalNetworking` doesn't permit the raw-IP fallback on device | Low–medium | Tested in acceptance step 7. Fallback per D3: `.local` only, or Debug-only arbitrary loads. |
| mDNS `.local` doesn't resolve over the Personal Hotspot | Medium | The raw-IP fallback is documented; step 7 records the result. |
| Local Network permission denied → every request fails like "can't connect" | Low | The transport message mentions checking Settings > Privacy > Local Network. |
| `X-Timezone` changes "today" for someone whose phone and server zones differ | Intended | Documented in §13 and the README. Acceptance steps 10–12 verify it and clean up. |
| A duplicate meal if the user retries after a client timeout while the server still saved | Low (the 300 s client timeout is above the server worst case of about 120 s) | No automatic retries. Idempotency keys are in Phase 3. |
| URLProtocol stub races under Swift Testing's parallelism | Medium | `.serialized` suite; one handler per suite. |
| `httpBody` is nil inside URLProtocol | Certain | Assert multipart through the pure builder (see §16). |
| The user's auto-reloading dev server reloads on branch checkout | Harmless this time | The backend code is identical apart from tests. Still use `git fetch . <branch>:main` for the fast-forward. |
| Scope creep into the store/redesign while touching the views | Medium | Task 6 is limited to a Retry button and one `nil` assignment. The review checks the diff against §4. |
